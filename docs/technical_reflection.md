# Technical Reflection

This project's four requirements — modularity, idempotency, storage trade-offs, and separating orchestration from business logic — are not four separate features bolted onto the pipeline. They are the same underlying discipline applied at four different points in the system: each layer knows only what it needs to know, and nothing more.

## Modularity

`src/extract/`, `src/transform/`, `src/load/`, `src/validate/`, and `src/benchmark/` each own exactly one responsibility, and none contains logic that belongs to another (`src/extract/` never applies business rules; `src/load/` never re-derives amounts). `src/cli.py` is a thin composition layer that wires these together but implements nothing itself. The practical payoff showed up directly in Goal 4: when the pipeline needed to run under Apache Airflow, not one line of `src/` changed. The DAG (`dags/dss150p_pipeline.py`) is a set of `python -m src.cli ...` calls with no transformation logic of its own, which is also why the unit tests in `tests/` run and pass with no Airflow installed at all — the modules under test were never coupled to the orchestrator that happens to invoke them in production.

## Idempotency

Every stage that writes anything is safe to rerun. `extract` re-verifies a raw snapshot against its own manifest hash rather than blindly re-copying; `load` and `load-partition` compare each row's `record_hash`, a SHA-256 of the business columns only, against what is already stored, and write nothing when the content is unchanged. This was proven directly, not assumed: `load` run twice reports `inserted=0 updated=0` on the second run (`docs/evidence/goal2_load.txt`), a full Airflow DAG run over already-loaded data reports `unchanged=49897` (`docs/evidence/goal4_full_run.txt`), and the Section 11 integrated test reproduces the same result a third time, from an independently fresh extraction (`docs/evidence/goal_section11_integrated_test.txt`). Idempotency is also what makes retries safe: with `retries=2` on every Airflow task, a retried `extract` or `load` repeats a no-op rather than repeating damage, because the underlying operation was already safe to run twice before Airflow ever entered the picture.

## Storage trade-offs

The Goal 3 benchmark measured CSV, JSON Lines, Parquet (snappy and zstd), and PostgreSQL against the same 49,897-row curated dataset rather than asserting a winner in the abstract. Parquet was smallest (24-38% of the CSV size) and fastest for both full and filtered reads, because it is columnar, typed, and compressed, while CSV must scan and parse every field before a filter can apply. That does not make Parquet universally correct: its files are immutable, so an update means rewriting the file, whereas PostgreSQL provides transactions, concurrent writers, and indexed lookups that Parquet has no equivalent for. The full comparison, with real medians and hardware context rather than rules of thumb, is in `docs/benchmark_report.md`.

## Orchestration versus business logic

Airflow's job in this project is exclusively to decide *when* and *in what order* work happens, never *what* the work computes. Every task in `dags/dss150p_pipeline.py` is a call into `src/`; the DAG's own code handles scheduling (`0 2 * * *`, `catchup=False`), retries, timeouts, parameters (`run_mode`, `year`, `month`), and a single run identity propagated to every task via `PIPELINE_RUN_ID={{ run_id }}`, so that `audit.pipeline_runs`, `audit.partition_loads`, and `audit.pipeline_run_events` all key on the same value regardless of whether a run was triggered manually or by the schedule. Keeping that boundary strict is also what kept the two systems' dependency requirements from colliding: Airflow 2.10.5's own official constraints pin older `pandas` and `pyarrow` than this pipeline needs, and because the pipeline's logic runs as its own process rather than inside Airflow's Python environment, it never has to adopt Airflow's pins.
